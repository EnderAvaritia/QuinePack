# V1 载荷上限为 1 GiB

## Status

accepted

## Context

自含压缩包生成需要随机访问整个产物、持有 seed 副本、做校验值定点并逐字节生成 quine 区的匹配指令；这些都不是流式一次扫描能完成的。若不设上限，就必须采用外存/流式架构，7z 头部与 CRC 定点的复杂度会显著上升，且难以在合理时间内完整验证。

## Decision

V1 对单次载荷设 1 GiB 硬上限。超过上限时在开始生成前明确报错，不得静默 OOM 或产生半成品。V1 验收使用 1 GiB 合成载荷；内存预算按产物体积的 2–3 倍设计。

## Considered Options

- 100 MiB：实现最简单，但排除了大量程序目录。
- 10 GiB：需要外存算法、64 位 tar 扩展与更强的性能优化，Python 可能不足。
- 不设硬上限：无法在合理时间内验证，且会让核心算法被迫流式化。

## Consequences

- 必须使用 mmap 或分块方式生成 quine 区指令，避免为每个匹配创建长生命周期的 Python 对象。
- CRC 定点必须利用 CRC 的线性性质做增量计算，不能对整文件反复重扫。
- CLI 需要给出载荷体积、预计内存与超限提示。
- 更大载荷属于后续版本，需要新的 ADR 取代本条。
