# CRC 定点改用解析列向量，不再逐位重扫归档

## Status

accepted

## Context

自含布局要在归档尾部写入自己的 CRC32：`7z-store` 的小 footer 解 96 位方程，
large footer 与 `7z` 的双层布局各解 128 位。每个未知量对应一个会被写回的 4 字节
槽位（header 里的 CRC 字段、header 副本、以及承载种子副本的那份镜像）。

原实现的做法是「逐位翻转 → 重算 `targets()` → 记录差值 → 翻回」。
`targets()` 里包含一次整份归档的 `_crc32(view)`，于是 96/128 个列向量
意味着 96/128 次全量扫描：

- 64 MiB：`7z-store` 5.6 s 里约 2.9 s 是这些扫描。
- 1 GiB：每次扫描约 0.35 s，合计约 45 s，是当时 `7z-store` 93 s 中的一半。

## Decision

CRC32 对消息是仿射线性的：翻转固定位置的一位，最终 CRC 的变化量只取决于
（位置、位号、缓冲区长度），与内容无关。据此新增三个工具函数：

- `_crc32_advance(register, zero_bytes)`：把 CRC 寄存器推过若干个清零字节，
  用 32 个预计算的 GF(2) 字节步进矩阵幂，按指数的二进制位依次作用。
- `_crc32_flip(positions, bit, start, length)`：区域内的翻位对 CRC 的增量。
- `_crc32_flip_tail(...)`：同一增量，但目标是一个后面还跟着 `tail` 字节的逻辑流片段，
  用于双层布局里「种子 = 压缩内容 + 前 32 字节 + header + plant + 填充」的拼接。

三个求解器（`_StoreBuilder.solve_crc`、`_solve_crc_large`、`_DoubleBuilder.solve_crc`）
保留各自的 `targets()`，但只在开头算一次基准向量；列向量全部解析求得，不再翻转缓冲区。
方程求解与写回逻辑不动，末尾的 `assert targets() == values` 保留为一次全量校验：
解析式一旦写错，断言会在构建时立刻失败，而不是产出坏归档。

## Considered Options

- **缓存翻转前的 CRC 再增量修正**：数学上等价，但要把「翻转状态」串进 `targets()`，
  比独立计算列向量更容易和既有代码走偏。
- **移植 zlib 的 `crc32_combine`（odd-matrix 多项式乘法）**：同样可行，
  但 32×32 矩阵幂的写法更直白，且不需要额外的多项式表示。
- **减少未知量（改布局让槽位不互相影响）**：会改变产物字节，破坏与既有基线的一致性。

## Consequences

- 全归档 CRC32 扫描从 96/128 次降到 1 次（外加末尾断言的一次校验）。
- 64 MiB 随机载荷：`7z-store` 5.6 → 2.7 s，`7z` 39.7 → 33.4 s。
- 256 MiB：`7z-store` 23.3 → 11.6 s，`7z` 224 → 157.7 s。
- 1 GiB：`7z-store` 93 → 46.9 s，`7z` 923 → 660.9 s，峰值工作集不变。
- 产物逐字节不变：64 MiB 三种格式的 SHA-256 与改造前一致，1 GiB 三种产物仍通过
  `7z t` / `xz -t` 与自含副本校验。
- 新增约 32 KiB 的常量表（32 个 32 位行向量），对启动时间无可见影响。
